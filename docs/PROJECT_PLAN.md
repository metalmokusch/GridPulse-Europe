# GridPulse Europe — project plan

## Product overview

GridPulse Europe is a self-hosted analytics application for recent electricity generation by source across a pilot set of European countries/zones. V1 targets a private trusted network deployment using Docker Compose, supports the 20 validated single zones, compares up to three countries, and does not persist source observations. It must show period, fetch time, source, unit, and quality/freshness. Missing or stale data must remain explicit. The deployed application has no AI/model dependency.

## Implementation plan

1. **Validate source and environment:** official ENTSO-E access, zone, generation semantics, rate-limit, and current terms reviewed. API access and short HU query are validated. A private, opt-in, non-persistent live mode has 20 active single bidding zones. A three-hour metadata-only check returned HTTP 200 with series for each; 16 were PT15M and four PT60M. Bulgaria and Great Britain returned no series in that sample and remain disabled. Written reuse clarification is required before exposing the service to others or publishing data.
2. **Record technical choices:** initial native Node.js/demo stack is recorded in ADR 0001. Revisit framework, package manager, chart library, and database only when the next vertical slice justifies them; document each change in an ADR.
3. **Bootstrap demo-first vertical slice:** complete. API health/readiness, synthetic fixture data, and a responsive dashboard with explicit time/unit/status and tabular fallback run without external credentials.
4. **Build data contracts and persistence:** provider-neutral UTC observation validation, versioned taxonomy, safe renewable-share calculation, and configurable freshness classifier are implemented and covered by offline tests. Country/zone distinction is preserved. A single-instance SQLite persistence boundary is the provisional direction; package choice, migrations, adapter-owned category maps, and idempotent storage remain open (see ADR 0004).
5. **Add provider adapter:** access and HU query behavior are validated. Private live mode is opt-in, server-side, and non-persistent. A configured EIC list exposes 20 verified-in-sample single bidding zones; Germany uses DE-LU and must be described as a combined zone. The adapter preserves either PT15M or PT60M periods and rejects mixed/unsupported resolutions. Wider exposure still requires written reuse clarification.
6. **Complete analytics and operations:** the responsive dashboard, Compose deployment, independent per-country failure display, and private deployment validation are complete. HU-only quality history is persisted to a host-mounted volume. Historical analytics, persistence of source observations, backup/restore, authentication, public exposure, and broader security review are outside the private-network V1 scope.

## Current state

- Standalone local Git repository connected to the public `metalmokusch/GridPulse-Europe` repository.
- First demo vertical slice implemented with native Node.js ESM, built-in HTTP, static HTML/CSS/JavaScript, synthetic HU/AT/DE fixtures, health/data endpoints, responsive dashboard, SVG chart, comparison cards, and table alternative.
- Dashboard controls support 6/12/24-hour chart windows and source-category filtering for the SVG chart and latest-value table. Country comparison and headline KPIs use successful selected-country responses; an error for one zone no longer hides the others.
- Dashboard country, period, and source selections are encoded in the URL so selected views can be shared and restored.
- Offline Node.js tests cover dashboard demo/live rendering, health, country/zone metadata, observation validation, UTC/unit/synthetic contracts, taxonomy, renewable-share completeness and arithmetic, freshness classification, dashboard URL state, ENTSO-E client/parsing/normalization and private live routes, privacy-safe quality monitoring, input validation, and static asset delivery.
- No third-party runtime dependencies or provider credentials are required. A GitHub Actions CI matrix targets Node.js 20, 22, and 24 with read-only repository permissions.
- GitHub Actions has successfully checked the dashboard and container build, using a Node.js 20/22/24 test matrix.
- Dockerfile and Compose configuration package the default fixture demo with a non-root user, read-only filesystem, dropped Linux capabilities, health check, and loopback-only default binding. The optional live overlay mounts a separate metadata-only quality log; source observations are not persisted. GitHub Actions builds the container image.
- Current ENTSO-E data-source findings and reuse terms are recorded in [data-sources.md](data-sources.md). The owner has authorized access and validated short HU requests. Private live mode is enabled by explicit configuration; sharing/publishing remains gated on reuse clarification and coverage policy.
- A separate manual ENTSO-E validation script sends a short HU request and reports only response metadata/category identifiers. It does not log response values or persist data. The token is read server-side from `ENTSOE_API_TOKEN` or `ENTSOE_API_TOKEN_FILE`; the default demo container receives no token.
- Dashboard URL state parsing and serialization live in a dependency-free browser module and are covered by offline tests for defaults, valid and invalid links, and serialization.
- An owner-run three-hour HU request returned HTTP 200, 15 time series, 126 points at PT15M resolution, and categories B01, B02, B04, B05, B06, B09, B11, B12, B14, B15, B16, B17, B19, and B20. This does not establish category completeness or equal series coverage.
- The full ENTSO-E B01–B20 source-code label dictionary and adapter mappings are recorded separately. B17 waste remains known-but-unclassified because source type alone does not identify its composition.
- A successful three-hour HU query reported 15 series with 126 points at PT15M. Thirteen categories had 11 points across 14:00Z–16:45Z; B06 appeared as three sparse series. Missing points are not assumed to mean zero, and coverage is not yet attested complete.
- The ENTSO-E XML normalizer creates domain observations, preserves series diagnostics, and always marks coverage incomplete. It maps all B01–B20 codes; B15/B13 map to `other_renewable`, B18 to offshore wind, B20 to non-renewable `other`, and B17 remains known-but-unclassified waste. B10 pumped hydro storage is a separate non-renewable category whose values may be negative while pumping. The taxonomy is version 1.2.0. The live HU client uses the normalizer at runtime but does not persist records. Offline tests cover every PSR code, signed B10 values, unknown source categories, sparse/repeated series, and malformed data. The default dashboard still reads synthetic fixtures.
- Opt-in `GRIDPULSE_DATA_SOURCE=entsoe` mode fetches per-country actual-generation data server-side for the 20 configured bidding zones, uses a five-minute per-zone in-memory cache, and does not persist provider data. The normal demo configuration remains synthetic. Compose has a separate ENTSO-E overlay for a file-backed token secret.
- Native `npm start` binds to loopback by default; the container listens internally on all interfaces while Compose publishes only to host loopback by default.
- Live dashboard labels identify ENTSO-E, show reported-only totals, leave missing intervals blank, and calculate renewable share from categories actually reported. Only mapped renewables enter the numerator; unknown/unclassified categories remain in the reported total and are never treated as renewable. Incomplete coverage is clearly labeled beside the percentage. Live mode is intended for private self-hosted deployments, not public exposure or redistribution.
- Live mode classifies age from the latest period end: fresh through 90 minutes, delayed through 3 hours, then stale. These provisional thresholds are documented in ADR 0005.
- Live mode refreshes automatically every 15 minutes; the manual refresh button bypasses the five-minute memory cache. Requests remain server-side and no observations are persisted.
- The private ENTSO-E Compose overlay runs an independent hourly HU-only quality check and appends metadata-only records to a persistent host-mounted JSONL log. The dashboard labels this history as HU-only and displays rolling 24-hour success, freshness, raw interval coverage, mature interval coverage after the H+1 publication grace window, pending recent intervals, failure classifications, and sparse category summaries. Production quantities and credentials are not logged.
- The private live container is running and healthy. Dashboard access was confirmed over the trusted home network. The first background check succeeded: 96/96 intervals had at least one reported category; B05, B06, and B09 were flagged by the heuristic sparse-category check. This was an initial sample, not a multi-day conclusion.
- Private deployment follow-up (2026-11-21): quality history showed successful checks interspersed with failures; one success had 94/96 intervals. A direct HU latest-data request returned HTTP 200 and fresh ENTSO-E data, while container logs contained only the startup line. The mounted token file was readable and non-empty. Historical failure causes remain unknown. The old normalizer rejected negative values for every category; ENTSO-E permits negative B10 pumped-storage values while pumping, so this was a possible code-level failure source, not a confirmed explanation. New builds persist only bounded failure classifications for future checks. Sparse B05/B06/B09 flags are heuristic category-frequency signals, not evidence by themselves of absent-data errors.
- Local iteration (2026-11-21): live renewable share reports the share of observed category totals even when coverage is incomplete; mapped renewable categories only enter the numerator, with B17/unknown included only in the denominator. Dashboard marks the result as reported-only. A three-hour metadata-only API check returned data for 20 configured one-zone countries, including PT60M for Belgium, Portugal, Latvia, and Switzerland; Bulgaria and Great Britain returned no series and remain disabled. The app's own 24-hour adapter successfully normalized all 20 zones without interpolation. `npm run check` and `npm test` pass (43/43).
- V1 readiness work: country series load independently and the dashboard reports failed selections while continuing to show successful countries. The public summary API returns partial results plus safe per-country error classifications. The monitoring panel and API explicitly identify HU as the only background-monitored zone. Validation: `npm run check`, `npm test` (44/44), and `git diff --check` passed.
- Private V1 deployment check (2026-11-22): the container was `healthy`; the HU–BE–AT comparison returned HTTP 200 with `partial: false` and no country errors. HU and AT returned 96 PT15M intervals, BE returned 24 PT60M intervals, and the quality-monitor API identifies HU as its monitored country.
- Private quality review (2026-11-22): the rolling 24-hour monitor window contained 25 checks, 25 successes, 0 failures, 98% mean raw interval coverage, and 100% mean mature interval coverage. The latest check observed 94/96 intervals; 92/92 mature intervals were present, with 2/4 recent pending intervals observed. B05/B06/B09 were flagged by the sparse-category heuristic. The Compose overlay stores the JSONL history on a host-mounted directory.
- Container restart check (2026-11-22): after restarting the app container, quality history advanced from 25 to 26 checks, all successful, with no failures; mature interval coverage remained 100% (92/92). Existing history therefore survived the container restart.
- Local V1 release-gate validation (2026-11-22): `npm run check`, `npm test` (44/44), and `git diff --check` passed. V1 was released for self-hosted Docker Compose use.

## External dependency backlog

- Review bounded failure classifications from future quality checks; historical failure causes cannot be recovered from existing logs.
- Review mature vs pending coverage in future quality logs to determine whether the observed 94/96 gaps were within the H+1 publication window; verify request-window boundaries over longer samples.
- Review the sparse-category heuristic and how the UI explains B05/B06/B09; do not assume low output means missing data or assume an omitted point means zero.
- B17 waste classification remains deliberately unresolved at the domain level because the source code alone does not identify renewable vs non-renewable feedstock.
- During private V1 deployment review, observe whether B10 appears, whether negative values occur, and whether the hourly HU quality check remains stable; do not infer historic causes from old log rows.
- Obtain written reuse clarification before exposing live data to other users or publishing API results or derived data.
